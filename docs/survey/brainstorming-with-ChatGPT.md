
# 技術トレンド調査システム 要件定義書

- バージョン: 0.6
- ステータス: 要件整理中
- 更新内容: 既存スキル再利用方針、AIエージェント運用方針を反映

## 1. 目的

技術分野の最新動向を継続的に収集・分析し、日次・週次レポートとしてGitHub Issuesに自動公開する。

主な目的は以下のとおり。

- 世界的な技術トレンドの把握
- 新しいOSS、AIモデル、ツール、サービスの発見
- 技術的に重要なリリースやアップデートの把握
- 複数の情報源を利用した重要度・実用性の評価
- 継続的な観測によるトレンドの変化の把握

将来的には、収集した情報を技術記事のテーマ発掘、追加調査、技術検証、記事作成に活用する。

ただし、記事の自動作成・公開はMVPの対象外とする。

## 2. 調査対象

### 2.1 技術カテゴリ

主な調査対象は以下とする。

1. 生成AI、LLM、AIエージェント
2. 開発者ツール、IDE、CLI、DevEx
3. クラウド、インフラ、DevOps
4. 注目度の高いOSS
5. AIが発見した隣接分野や新しい技術テーマ

固定カテゴリを優先しつつ、重要な新規テーマも収集する。

### 2.2 情報源

以下の情報源を対象とする。

- GitHub
  - 新規OSS
  - リリース
  - Starなどの成長指標
- Hacker News
- Reddit
- X / Twitter（取得可能な範囲）
- 公式ブログ、リリースノート、RSS
- arXivなどの論文情報
- その他の技術コミュニティ

追加候補として以下を検討する。

- Hugging Face
- Lobsters
- CNCF関連情報
- Dev.to
- Zenn / Qiita
- Product Hunt
- Stack Overflow

実際に利用する情報源は、API利用条件、取得品質、実装負荷を確認して決定する。

### 2.3 対応言語

- 日本語・英語の情報を積極的に収集する
- 世界的な技術トレンドを把握する
- 日本語と英語の比較自体は目的としない
- 最終レポートは日本語で作成する
- 原文のURLと情報源を保持する

## 3. 日次レポート

### 3.1 実行頻度

- 1日1回
- JSTの翌朝に実行する
- 対象期間は前日00:00〜当日00:00（JST、終了時刻は含まない）
- 具体的な実行時刻は未定

### 3.2 内容

前日に発生した重要な技術情報を収集・整理する。

特に以下を重視する。

- 新しいAIモデルの発表・リリース
- 新しいOSS・ツール・サービス
- 重要なバージョンアップ
- 開発者に影響する技術的な変更
- 注目を集めた技術ニュース
- 実用性の高い技術情報

速報専用の実行ジョブは設けない。

### 3.3 出力

- GitHub Issueを1件作成する
- IssueをGitHub Projectsに自動登録する
- 目安は10〜20件程度
- 重要な情報が多い場合は件数を柔軟に変更する
- 情報源・公開日・重要性・技術的な要点を記載する

## 4. 週次レポート

### 4.1 実行頻度

- 毎週月曜日に実行する
- GitHub Issueを1件作成する
- GitHub Projectsに自動登録する

### 4.2 目的

日次レポートの単純な再掲ではなく、技術トレンドを分析する。

主な内容は以下とする。

- 注目技術の変化
- 新たに台頭したテーマ
- 継続して注目されている技術
- OSSやツールの比較
- 重要な技術的変化
- 今後注目する価値のあるテーマ

### 4.3 調査期間

調査期間は設定可能な構成を目指す。

既存のlast30daysスキルを利用する都合で30日間のローリング検索を検討していたが、30日間は必須要件ではない。

以下を検証して決定する。

- 既存スクリプトで取得期間を変更できるか
- 7日・30日などの期間で取得品質がどう変わるか
- 取得量とAPIコスト
- 既存SQLiteデータの再利用可能性
- 期間を重複させた際のトレンド評価方法

週次の再検索範囲はPoCで実測したうえで決定する。

## 5. 既存スキルの再利用

### 5.1 基本方針

以下のリポジトリを参考・再利用対象とする。

https://github.com/mvanhorn/last30days-skill

- `npx skills add` による導入を第一候補とする
- 既存スキル本体の調査フローをそのまま利用することは前提としない
- 既存スキルに含まれる情報収集スクリプトを再利用する
- CLI・APIを利用した取得処理を可能な限り活用する
- 既存のSKILL.mdを参考に独自スキルを作成する

### 5.2 独自スキル

以下のスキルを作成する想定とする。

- 日次情報収集・レポート生成スキル
- 週次情報収集・トレンド分析スキル

両スキルは共通の収集処理を利用する。

### 5.3 依存関係管理

第一候補は`npx skills add`とする。

ただし、Docker・cronでの無人実行に必要な再現性を検証する。

比較対象は以下とする。

- `npx skills add`
- Git Submodule
- 特定コミットの固定取り込み
- 必要なコードのみの再利用

最終方式はPoC後に決定する。

### 5.4 検証事項

- 取得期間を変更できるか
- 収集スクリプトを単独実行できるか
- SKILL.mdと収集処理を分離できるか
- Claude CodeとCodexの両方から利用できるか
- 実行に必要な認証・環境変数・依存パッケージ
- 出力形式の統一方法
- 上流更新への追従方法
- ライセンスと再利用条件

## 6. AIエージェント

### 6.1 実行環境

- Claude Codeを利用可能とする
- Codexも利用可能とする
- 利用者が状況に応じて切り替える
- 両者の性能・コスト比較は不要
- セッション切れを検知した自動切り替えも不要

### 6.2 責務分離

AIエージェントが担当する処理：

- 収集情報の意味的な評価
- 重要度の判断
- 関連技術との比較
- 必要な追加調査
- トレンド分析
- レポート文章の生成

Python・CLI・APIが担当する処理：

- スケジュール管理
- データ取得
- 日付・期間の計算
- URL正規化
- 重複排除
- SQLiteへの保存
- ジョブ状態管理
- GitHubへの登録
- リトライ処理

LLMを使用する必要のない決定的処理は、原則としてプログラムで実装する。

### 6.3 調査深度

技術カテゴリごとに調査深度を変更する。

例：

- 新モデル・新サービス：発表内容と一次情報を優先
- OSS：機能、実用性、技術的特徴を確認
- 技術トレンド：複数情報源と過去の変化を分析
- 重要度の低い情報：簡潔に要約

## 7. データ管理

### 7.1 SQLite

SQLiteを利用して以下を管理する。

- 収集した情報
- 情報源・URL・取得日時
- 公開日時
- 取得成功・失敗
- 重複判定結果
- AI分析結果
- 調査期間
- レポート生成履歴
- GitHub Issueとの対応関係
- 実行ジョブとエラー履歴

データは最低1年間保存する。

### 7.2 GitHubとの責務分離

SQLiteは収集・分析・実行履歴を管理する。

GitHubは以下を管理する。

- IssueのOpen / Closed
- Projectsのステータス
- 人間によるコメント・編集
- レポートの閲覧・管理

GitHub側の状態をSQLiteで二重管理しない。

### 7.3 重複防止

日次・週次レポートに一意なキーを付与する。

- 同じ期間のIssueを重複作成しない
- 再実行時は既存Issueを確認する
- GitHub API失敗後の再実行でも重複登録を防ぐ

## 8. GitHub連携

- 公開リポジトリを利用する
- 個人GitHub Projectsを利用する
- 日次・週次レポートをIssueとして自動作成する
- Issue作成後、Projectsに自動登録する
- MVPでは既存Issueへの追加調査・追記は行わない
- IssueのステータスやProjectsの状態を自動変更しない

## 9. 品質管理

### 9.1 評価観点

- 正確性
- 一次情報の有無
- 情報の新規性
- 技術的な重要性
- 実用性
- ノイズの少なさ
- 情報源の信頼性

### 9.2 自動検証

以下を可能な範囲で自動検証する。

- 必須項目の存在
- URL形式
- 対象期間との整合
- 重複情報
- レポート件数
- 情報源の記載
- Issueの重複登録

### 9.3 人間による評価

- レポートの有用性を定期的に確認する
- 見逃しや誤検出を評価する
- 評価結果を収集ルールやプロンプトに反映する

## 10. 障害対応・運用

### 10.1 実行環境

- 個人VPSまたはサーバー
- Dockerを利用する
- cronによる定期実行
- 小規模な構成から開始する

### 10.2 障害時の処理

- APIや収集処理の失敗時は再試行する
- 一部の情報源が復旧しない場合は部分レポートを許容する
- 取得できなかった情報源を記録する
- GitHubへの登録失敗時は再実行可能にする

### 10.3 監視

MVPでは最低限のログのみ実装する。

外部通知や監視システムは後続フェーズで検討する。

## 11. MVP対象範囲

MVPに含める機能：

- 日次レポート生成
- 週次レポート生成
- 既存スキルの収集処理の再利用
- 独自SKILL.mdの作成
- Claude Code / Codexからの利用
- SQLiteへの保存
- GitHub Issue作成
- GitHub Projects登録
- 重複防止
- 基本的なリトライ
- 最低限のログ
- 自動品質検証

MVPに含めない機能：

- 速報専用の高頻度実行
- Issue公開後の自動追記
- Claude / Codexの自動切り替え
- モデル性能・コスト比較
- 高度な監視・通知
- 記事の自動執筆・公開
- 複雑な技術ランキング
