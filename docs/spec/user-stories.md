# ユーザストーリー（What - 小）

[epics.md](epics.md) の MVP エピックを、ペルソナ（[concept.md](concept.md#ペルソナ)）にとっての価値の単位に分解する。

- 書式：「〈ペルソナ〉として、〈したいこと〉。なぜなら〈理由〉」
- 優先度：Must（MVPに必須）／Should（MVPで実現したい）／Could（余裕があれば）／MVP外（MVP に含めないと決めたもの。括弧内に元の優先度を書く）
- 受け入れ条件：価値が届いたと判断できる状態のみを書き、実装方式は書かない
- 「未確定」：PoC・設計で決める事項（[concept.md](concept.md#未確定事項)）
- 「D-xx」：決定した実現方式（[decisions.md](decisions.md)）

## Issue の種別

ストーリー中で使う Issue の種別。種別はラベルで区別する（ラベル名は [decisions.md](decisions.md#d-08-issue-のラベル名) の D-08）。

| 種別 | 作成する場面 |
|---|---|
| レポート Issue | 日次・週次レポートが自動検証に合格したとき |
| 不合格 Issue | レポート全体が自動検証に不合格だったとき（レポート Issue の代わりに作成） |
| 実行エラー Issue | リトライを使い切ってもジョブが完了しなかったとき、または公開前の検査で秘匿情報が検出されたとき |

## E1 技術情報の収集

### US-E1-01 重点領域の情報を日英の複数情報源から集める（Must）

読者として、重点領域の情報を日本語・英語の複数情報源から集めてほしい。なぜなら自分で巡回しなくても重要な動向を見落とさずに済むから。

- 生成AI・LLM・AIエージェント、開発者ツール、クラウド・インフラ、注目度の高いOSSの情報が収集対象になっている
- 日本語・英語の両方の情報源から収集している
- 各情報に、情報源・URL・公開日時（不明な場合は投稿日時）・取得日時が保持されている
- 対象期間内に起きた出来事（公開・リリース・注目の急上昇）の情報のみが残り、それ以外は除外されている
- 元記事の公開日時が不明な情報は、情報源への投稿日時で判定されている
- 再利用方式は [D-01](decisions.md#d-01-last30days-skill-の取り込み方式)、自作範囲は [D-03](decisions.md#d-03-自作する収集処理)、初期の情報源は [D-11](decisions.md#d-11-情報源の初期セットと費用) で決定
- 注目の急上昇として一度日次レポートに掲載された記事・リポジトリは、その後の日次レポートに急上昇として再び掲載されない（注目が続いていることは週次で扱う）
- 注目の急上昇の判定方法は [D-13](decisions.md#d-13-注目の急上昇の扱い)（しきい値は PoC で調整）
- 注記（対象期間の扱い）：人気型フィードへの初登場と GitHub の Star の増分は、毎朝の取得（6:00）どうしで測るため、対象期間の代わりに対象日 6:00〜翌日 6:00 の24時間で判定する（D-13）

### US-E1-02 重点領域外の新しいテーマも拾う（Must）

読者として、重点領域に当てはまらない新しい技術テーマも拾ってほしい。なぜなら固定カテゴリの外で台頭するテーマを見落としたくないから。

- 重点領域に属さない情報も、重要と判断されれば「その他の新テーマ」として収集結果に残る

### US-E1-03 同じ話題を1件にまとめる（Must）

読者として、同じ話題が複数の情報源にあっても1件にまとめてほしい。なぜなら同じ内容を何度も読まずに済むから。

- 同じURL（表記ゆれを含む）を指す情報は1件になっている
- 同じ出来事を扱う複数の情報は1項目にまとめられ、出典が併記されている

### US-E1-04 一次情報を優先する（Must）

読者として、一次情報を優先して確認できるようにしてほしい。なぜなら二次情報の誤りや誇張に左右されたくないから。

- 一次情報（公式発表・リリースノート・リポジトリ・論文など）が特定できる場合、出典の先頭に一次情報のURLがある

## E2 日次レポート

### US-E2-01 前日の重要情報を毎朝読む（Must）

読者として、前日の重要な技術情報を日本語のレポートで毎朝読みたい。なぜなら短時間で前日の動向を把握できるから。

- 対象期間は前日00:00〜当日00:00（JST、終了時刻は含まない）
- 自動検証に合格した場合、対象日につきレポート Issue が1件作成される（合格しない場合は不合格 Issue または実行エラー Issue が作成される）
- レポートは日本語で書かれている
- 実行時刻は [D-09](decisions.md#d-09-実行時刻) で決定（毎朝 6:00 JST）

### US-E2-02 重要な情報に絞って10分前後で読む（Must）

読者として、重要な情報を10〜20件程度に絞ってほしい。なぜなら10分前後で読み切りたいから。

- 掲載件数の目安は10〜20件で、重要な情報が多い日は柔軟に増減する
- 新しいAIモデル、新しいOSS・ツール・サービス、重要なバージョンアップ、開発者に影響する変更、注目を集めたニュース、実用性の高い情報が優先して選ばれている
- 選定の妥当性は人による評価で確認する（US-E7-03）

### US-E2-03 各項目の要点と重要性を読む（Must）

読者として、各項目で何が新しく、なぜ重要かを読みたい。なぜなら原文を開くかどうかをすぐ判断したいから。

- 各項目に、日本語の見出し・カテゴリ・要点・重要性の理由・情報源名と公開日（不明な場合は投稿日）・出典URLがある
- 公開が対象期間より前で、期間内に注目が急上昇した項目は、期間内に何が起きたかが分かる
- テンプレートは [D-15](decisions.md#d-15-レポートのテンプレート) で決定

### US-E2-04 カテゴリごとに読み進める（Must）

読者として、レポートをカテゴリごとに整理してほしい。なぜなら関心のある分野から読み、他は読み飛ばしたいから。

- 項目がカテゴリ単位にまとまって並んでいる

### US-E2-05 情報の種類に応じた深さで読む（Should）

読者として、情報の種類に応じた深さで調査・要約してほしい。なぜなら重要な情報は詳しく、重要度の低い情報は簡潔に読みたいから。

- 新モデル・新サービスは、発表内容と一次情報にもとづいて書かれている
- OSSは、機能・実用性・技術的特徴が書かれている
- 重要度の低い情報は簡潔に要約されている
- 一次情報の集め方は [D-14](decisions.md#d-14-一次情報の本文の集め方) で決定
- 注記（MVP での達成範囲）：AI 系の公式発表のうち、公式 RSS に本文が載らないもの（Google AI・DeepMind・Hugging Face・Anthropic など）は、MVP では要約と二次情報をもとに書く。記事ページの取得は将来対応の Issue（D-08）に書く。OpenAI はページの取得を拒否されるため、その後も要約と二次情報で書く見込み

### US-E2-06 重要情報が少ない日もレポートを受け取る（Must）

読者として、重要な情報がほとんどない日もレポートを受け取りたい。なぜなら「Issue がない＝ジョブが失敗した」と判断できるようにしたいから。

- 収集結果が0件、または重要な情報がほとんどない日も、その旨を明記したレポート Issue が1件作成される（すべての情報源が取得できない場合は US-E6-04、除外で0件になった場合は US-E7-02）

## E3 週次トレンド分析レポート

### US-E3-01 毎週月曜に週次トレンド分析を読む（Must）

読者として、毎週月曜に技術トレンドの分析レポートを読みたい。なぜなら日々の断片的な情報からは見えない変化を把握したいから。

- 自動検証に合格した場合、毎週月曜にレポート Issue が1件作成される（合格しない場合は不合格 Issue または実行エラー Issue が作成される）
- レポートは日本語で書かれ、各項目に出典URLがある
- 個別ニュースの列挙ではなく、テーマ単位で調査期間内の変化が書かれている
- テンプレートは [D-15](decisions.md#d-15-レポートのテンプレート) で決定
- 未確定：調査期間（PoCで決定。設定で変更できる。US-E8-01）

### US-E3-02 台頭・継続・沈静したテーマを知る（Must）

読者として、新たに台頭したテーマ、継続して注目されているテーマ、注目が落ち着いたテーマを知りたい。なぜならトレンドの変化を捉えたいから。

- 新たに台頭したテーマ、継続して注目されている技術、注目が落ち着いたテーマが区別して書かれている
- 期間内の重要な技術的変化が書かれている
- 判断の根拠として、蓄積した過去の観測との比較が示されている

### US-E3-03 OSS・ツールの比較を読む（Should）

読者として、注目されたOSSやツールの比較を読みたい。なぜなら似た選択肢の違いを把握して、試すものを選びたいから。

- 同じ領域で注目されたOSS・ツールについて、特徴の違いが比較されている

### US-E3-04 今後注目すべきテーマを知る（Should）

読者として、今後注目する価値のあるテーマを知りたい。なぜなら次に追いかける対象を決めたいから。

- 今後注目する価値のあるテーマが、理由とともに挙げられている

## E4 GitHub への公開

### US-E4-01 レポートを GitHub Issue で読む（Must）

読者として、レポートを公開リポジトリの GitHub Issue で読みたい。なぜなら普段使う GitHub 上で閲覧・管理したいから。

- 日次・週次のレポートが、公開リポジトリにレポート Issue として作成される
- Issue に認証情報や秘匿情報が含まれていない

### US-E4-02 Issue を Projects で一覧する（Must）

読者として、作成された Issue が個人 GitHub Projects に自動登録されてほしい。なぜなら Projects でレポートと失敗の状況をまとめて把握したいから。

- レポート Issue・不合格 Issue・実行エラー Issue が Projects に登録される
- Issue の種別がラベルで区別できる
- ラベル名・Projects 登録の認証方式は [D-08](decisions.md#d-08-issue-のラベル名)・[D-05](decisions.md#d-05-認証情報の渡し方) で決定

### US-E4-03 同じ期間のレポートを重複させない（Must）

読者として、同じ期間のレポート Issue が重複しないでほしい。なぜなら同じレポートが複数あると混乱するから。

- 同じレポート（日次は対象日、週次は対象週＝本来の実行日であるその週の月曜の日付で判定し、調査期間の設定は含めない）のレポート Issue が既にあれば、Open / Closed を問わず新たに作成されない
- Issue 作成後に Projects 登録だけが失敗した場合、次の実行（日次・週次のどちらでもよい）が、Issue を作り直さずに登録を完了させる。対象はレポート Issue・不合格 Issue・実行エラー Issue のすべて
- 登録だけの失敗では実行エラー Issue を作らず、ログと履歴に記録する
- 自動の再試行（US-E6-02）で同じ処理が再び動いても、レポート Issue は重複しない

### US-E4-04 公開後の Issue を自動で変更しない（Must）

読者として、公開後の Issue の状態・本文・コメントを自動で変更しないでほしい。なぜなら自分で付けたコメントや管理状態を壊されたくないから。

- 公開済み Issue の本文・Open/Closed・Projects のステータス・コメントが自動で変更されない

## E5 収集・分析履歴の蓄積

### US-E5-01 収集情報と分析結果を蓄積する（Must）

運用者として、収集した情報と分析結果を保存したい。なぜなら週次分析で過去の観測と比較し、後から経緯を確認したいから。

- 収集情報・情報源・URL・取得日時・公開日時・重複判定結果・AI分析結果・調査期間が保存されている
- データが最低1年間保持される
- 未確定：テーブル設計、共通収集データのスキーマ

### US-E5-02 実行の成否とエラーを後から確認する（Must）

運用者として、実行ジョブの成否とエラーの履歴を確認したい。なぜなら障害の原因を調べて復旧したいから。

- ジョブごとの対象期間・開始/終了・成否・エラー内容が保存されている
- 情報源ごとの取得の成功・失敗が保存されている
- Projects への登録だけが失敗したジョブは、成功として記録され、登録の失敗が別に記録されている（US-E4-03）

### US-E5-03 レポートと Issue の対応を追跡する（Must）

運用者として、どのレポートがどの Issue になったかを追跡したい。なぜなら重複防止と障害調査に使いたいから。

- レポート生成履歴と、作成した Issue（レポート・不合格・実行エラー）の対応が保存されている
- GitHub 側の状態（Open/Closed、Projects のステータス、コメント）は保存されていない。Projects への登録を済ませたかどうかは、自分の処理の記録として保存する（US-E4-03）

## E6 無人定期実行と障害復旧

### US-E6-01 無人で定期実行する（Must）

運用者として、日次・週次を人手を介さず定期実行したい。なぜなら毎回手で実行せずにレポートを受け取りたいから。

- 個人VPS・サーバー上の Docker と cron で、日次は毎朝、週次は毎週月曜に実行される
- 実行に人の操作を必要としない
- 認証情報は環境変数から読まれ、コード・ログ・Issue に出力されない
- 認証は [D-05](decisions.md#d-05-認証情報の渡し方)、API 費用の上限（月 $0）は [D-11](decisions.md#d-11-情報源の初期セットと費用) で決定
- 未確定：API 利用量・実行時間の許容上限

### US-E6-02 一時的な失敗を自動で再試行する（Must）

運用者として、API や収集処理の一時的な失敗を自動で再試行してほしい。なぜなら一時的な障害のたびに手で復旧したくないから。

- 失敗した処理が自動で再試行される
- 再試行で成功した場合、レポートは通常どおり公開される
- 未確定：再試行回数の上限、API利用量・実行時間の許容上限

### US-E6-03 一部の情報源が失敗してもレポートを受け取る（Must）

読者として、一部の情報源が取得できなくてもレポートを受け取りたい。また、何が欠けているかを知りたい。なぜなら「載っていない＝重要でなかった」と誤解したくないから。

- 日次・週次ともに、一部の情報源が再試行後も取得できない場合、残りの情報源でレポート Issue が作成される（1つでも取得できれば部分レポートとする）
- すべての情報源が取得できない場合は、実行エラー Issue が作成される（US-E6-04）
- レポート本文の末尾に、取得できなかった情報源が明記されている
- 取得できなかった情報源が記録されている

### US-E6-04 復旧しない失敗を実行エラー Issue で知る（Must）

運用者として、再試行しても完了しなかったジョブを Issue で知りたい。なぜなら普段見る GitHub 上で失敗に気づき、対応したいから。

- 再試行を使い切ってもジョブが完了しなかった場合（すべての情報源が取得できない場合を含む）、実行ごとに実行エラー Issue が1件作成される。Projects への登録だけの失敗は除く（US-E4-03）
- 実行エラー Issue に、対象期間・失敗した処理段階・エラーの概要・再試行回数と、失敗の調査結果（US-E7-04）が書かれている（秘匿情報検出による定型の実行エラー Issue（US-E7-05）は除く）
- スタックトレース・生ログの全文は書かれていない
- GitHub 自体に登録できない失敗の場合は、ログと履歴にのみ記録される（MVPの制約）

### US-E6-05 失敗の後は次の定時の実行から再開する（Must）

運用者として、失敗した日・週のレポートは作り直さず、次の定時の実行から通常どおり再開したい。なぜなら数日後に過去の日のレポートを受け取っても読まないから。

- 失敗した対象日・対象週のレポートは、後から作り直さない（過去の期間を指定して実行する機能は持たない）
- 失敗の後の定時の実行は、運用者の操作なしに通常どおりレポート Issue を作成する
- 前日の記録がなく注目の急上昇を判定できない情報源があれば、日次レポートのヘッダに、判定ごとにその旨と情報源名が1行書かれ、部分レポートにはならない（[D-13](decisions.md#d-13-注目の急上昇の扱い)）
- 実行ジョブの履歴は実行ごとに追加される

### US-E6-06 最低限のログで実行状況を確認する（Must）

運用者として、実行状況をログで確認したい。なぜなら異常時に何が起きたかを調べたいから。

- ジョブの開始・終了・処理段階・失敗がログに出力される
- ログに認証情報や秘匿情報が出力されない

## E7 レポート品質の担保

### US-E7-01 公開前にレポートを自動検証する（Must）

読者として、公開前にレポートを自動で検証してほしい。なぜなら不正確な情報や壊れたレポートを読みたくないから。

- 必須項目の存在、URL形式、対象期間との整合、重複、件数、情報源の記載が検証される
- 項目単位の不備（URL不正・対象期間外・重複など）がある項目は除外されてレポートが公開される
- 除外した項目はログと履歴に記録され、Issue には書かれない

### US-E7-02 不合格になったレポートを不合格 Issue で知る（Must）

運用者として、レポート全体が検証に不合格だった場合、そのことを Issue で知りたい。なぜなら何が起きたかを確認し、プロンプトや収集ルールの改善に使いたいから。

- レポート全体の不備（必須セクションの欠落、項目0件なのに「該当なし」の明記がない等）がある場合、レポート Issue の代わりに不合格 Issue が作成される
- 件数はレポート全体の検証として扱い、目安（10〜20件）からの増減だけでは不合格にならない。件数で不合格となるのは、0件なのに「該当なし」の明記がない場合と、次の除外による0件の場合のみ
- 収集結果があるのに、項目の除外によって掲載項目が0件になった場合は不合格 Issue が作成される
- 不合格 Issue に、対象期間・不合格となった検証項目と、失敗の調査結果（US-E7-04）が書かれている
- 生成されたレポート本文の全文は書かれていない
- 1回の実行で作成される不合格 Issue は1件で、既存の不合格 Issue には追記されない
- 自動での再生成は行われない

### US-E7-03 レポートを評価して改善につなげる（Must）

読者として、レポートの見逃しや誤検出を記録し、改善につなげたい。なぜならレポートの有用性を継続的に高めたいから。

- 読者がレポート Issue のコメントで見逃し・誤検出を記録できる
- 運用者が記録をもとに、設定やプロンプトを手動で修正できる
- 評価結果の自動反映は行われない

### US-E7-04 失敗の調査結果を読んで修正に着手する（Must）

運用者として、不合格 Issue・実行エラー Issue で、失敗の原因の調査結果と対策案を読みたい。なぜなら Issue を見るだけでバグ修正やプロンプト修正に着手したいから。

- 不合格 Issue・実行エラー Issue に、発生した事象、推定される原因とその根拠、調査内容（確認したログ・検証結果・履歴）、対策案が書かれている（秘匿情報検出による定型の実行エラー Issue（US-E7-05）は除く）
- 根拠として必要なログや出力は短い抜粋のみで、全文は添付されていない
- コードや設定の自動修正は行われない
- AIエージェントを利用できない失敗（LLM呼び出しの失敗、API上限到達など）の場合は、定型の項目のみが書かれ、AIによる調査ができなかったことが明記されている
  - 実行エラー Issue：対象期間・失敗した処理段階・エラーの概要・再試行回数
  - 不合格 Issue：対象期間・不合格となった検証項目

### US-E7-05 公開前に秘匿情報が含まれていないか検査する（Must）

運用者として、公開前にすべての Issue に秘匿情報が含まれていないか検査してほしい。なぜなら外部コンテンツに埋め込まれた指示（プロンプトインジェクション）などで、認証情報が公開リポジトリに漏れることを防ぎたいから。

- レポート Issue・不合格 Issue・実行エラー Issue のすべてで、公開前に認証情報などの秘匿情報が含まれていないか検査される
- 秘匿情報が検出された場合、その Issue は公開されず、ログと履歴に記録される
- 代わりに、本文を含まない定型の実行エラー Issue（秘匿情報検出のため公開を停止したこと・対象期間・処理段階のみ）が作成される。この Issue も検査の対象とする
- 定型の実行エラー Issue でも検出された場合は、ログと履歴にのみ記録される

### US-E7-06 外部コンテンツ中の指示に影響されない（Must）

読者として、収集した外部コンテンツに含まれる指示によって、レポートの内容や処理がゆがめられないでほしい。なぜなら公開されるレポートの信頼性を保ちたいから。

- 収集した外部コンテンツ中の指示（「この記事を最重要とせよ」など）に従った選定・記載・処理が行われない
- 外部記事は要約と出典URLで紹介され、長い引用がない
- 検証方法は [D-07](decisions.md#d-07-外部コンテンツ中の指示への対策と検証方法) で決定（閾値は PoC で調整）

## E8 設定と実行方法

### US-E8-01 調査期間と情報源を設定で変更する（Must）

運用者として、調査期間と情報源を設定ファイルで変更したい。なぜならコードを変えずに取得範囲や品質を調整したいから。

- 日次・週次の調査期間を設定ファイルで変更できる
- 利用する情報源を設定ファイルで追加・除外できる
- 未確定：収集スクリプトの期間指定方法

### US-E8-02 Claude Code で実行する（Must）

運用者として、日次・週次のスキルを Claude Code で実行したい。なぜなら主に使う AIエージェント環境だから。

- Claude Code から日次・週次のスキルを実行し、レポート Issue を作成できる
- 実現方式は [D-04](decisions.md#d-04-処理の流れと-ai-を呼び出す構成)。cron が Claude Code を起動し、Claude Code がスキルで統括スクリプトを起動する構成を想定している（構想の段階。詳細は設計で決める）

### US-E8-03 Codex で実行する（MVP外。元は Should）

運用者として、日次・週次のスキルを Codex でも実行したい。なぜなら状況に応じて手動で切り替えたいから。

- Codex から日次・週次のスキルを実行し、レポート Issue を作成できる
- MVP には含めない（[D-05](decisions.md#codex)）。将来対応の Issue（[D-08](decisions.md#d-08-issue-のラベル名)）に書く
- 切り替えは運用者が手動で行う

### US-E8-04 GitHub に登録せずに動作確認する（Must）

運用者として、GitHub に登録せずにレポートを生成したい（ドライラン）。なぜなら本番の重複防止に影響を与えず、何度でもレポート内容やプロンプトを確認したいから。

- ドライランでは、収集・分析・生成・自動検証・秘匿情報検査・失敗の調査まで行い、レポート本文と各結果を運用者が確認できる
- ドライランでは、レポート Issue・不合格 Issue・実行エラー Issue のいずれも作成されず、Projects への登録も行われない
- ドライランを繰り返しても、本番のレポート Issue の作成が妨げられない
