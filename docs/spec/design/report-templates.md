# レポートのテンプレート

レポート Issue（日次・週次）・不合格 Issue・実行エラー Issue の本文の形式と、重複防止用の識別子を定める（[decisions.md](../decisions.md#d-15-レポートのテンプレート) の D-15）。文字数の上限・「少ない日」のしきい値・週次の比較の窓などの数値は PoC で調整する。記入例の中身はすべて架空である。

## 0. 前提と共通ルール

### 0.1 テンプレートが満たす要件

| 出典 | テンプレートへの要求 |
|---|---|
| US-E2-01・E3-01 | 日本語。日次は前日（JST）分、週次は毎週月曜。対象期間につき1件 |
| US-E2-02 | 10〜20件程度、10分前後で読み切れる |
| US-E2-03 | 各項目に、日本語の見出し・カテゴリ・要点・重要性の理由・情報源名と公開日（不明なら投稿日）・出典URL。期間前に公開され期間内に急上昇した項目は、期間内に何が起きたかが分かる |
| US-E2-04 | カテゴリ単位にまとめて並べる |
| US-E2-05（Should） | 重要度に応じて詳しさを変える |
| US-E2-06 | 0件・ほとんどない日も、その旨を明記したレポート Issue を作る |

### 0.2 記法：誰が書くか

テンプレート中のプレースホルダは次の2種類で書き分ける。

| 記法 | 書く主体 | 段階（D-04） | 内容 |
|---|---|---|---|
| `{{C: …}}` | コード | ③ 検証・検査、⑤ 投稿 | 日付・件数・見出しの枠・カテゴリ名・出典（情報源名・日付・URL）・取得できなかった情報源・識別子・定型文 |
| `{{AI: …}}` | AI | ② 評価・要約、④ 失敗時の調査 | 見出し・要点・重要性の理由・期間内の出来事・テーマ分析・調査結果などの日本語の文章 |

繰り返し部分（項目やテーマの並び）は `{{C+AI: …}}` と書く。コードが枠と出典を作り、AI の部品（`{{AI: …}}`）を流し込む部分を表す。

AI は Markdown の本文を組み立てない。AI は文章の部品と ID だけを決まった形式のデータで返し（標準出力の JSON。D-04）、コードがテンプレートに流し込んで Issue 本文を作る。テンプレートが使う AI の出力は次のとおり。出力スキーマの詳細は設計で決める。

- 日次の各項目：`item_ids`（同じ出来事としてまとめた収集項目）、`primary_item_id`・`primary_link_id`（一次情報。D-06）、見出し、`category`（enum）、要点（配列）、重要性の理由、期間内の出来事、`depth`（`full`／`brief`）、`rank`（カテゴリ内の重要度順）
- 週次の各テーマ：テーマ名、期間内の変化、過去の観測との比較、`item_ids`（今週の観測）、`past_ids`（コードが渡した過去の観測）、状態（enum：`rising`／`steady`／`fading`）
- 週次の重要な技術的変化：見出し、説明、`item_ids`（出典）
- 週次の OSS・ツールの比較：領域名、各行の `item_id` または製品名、特徴、向いている用途、違いのまとめ
- 週次の今後注目すべきテーマ：テーマ名、理由、`item_ids`（根拠）
- 失敗時の調査：発生した事象、推定される原因と確度、調査内容、対策案、`evidence_line_ids`（根拠に使うログ行の ID）

理由：本文の構造（見出し・表・折りたたみ・識別子）をコードが握れば、AI の出力が崩れても枠は壊れず、D-07 の検査（D2・D3・D6）を部品ごとにかけられる。トレードオフは、AI が文章の構成を自由に変えられないこと（週次で特に効く）。

### 0.3 コードが行う整形と無害化

AI の出力テキストと外部由来の文字列は、テンプレートに入れる前にコードが次の処理を行う。

| 対象 | 処理 | 理由 |
|---|---|---|
| AI テキスト全般 | 改行を除き1段落にする（要点は配列の1要素＝1行）。行頭の `#`・`>`・`-`・`1.` などのブロック記法をエスケープする | 見出しや引用を勝手に作らせず、構造を壊させない |
| AI テキスト全般 | 次の文字列をインラインコード（`` ` ``）で囲む：`@ユーザー名`、`@org/team`、`#数字`、`GH-数字`、`owner/repo#数字`、コミット SHA（7〜40桁の16進数で、`a`〜`f` の英字を1文字以上含むもの。数字だけの列は対象外）、`owner/repo@SHA` | GitHub は Issue 本文の `@ユーザー名`・`@org/team` をメンションとして通知し、`#数字`・`GH-数字` などを Issue への参照、SHA をコミットへの参照としてリンクし、参照先に記録を残す。公開リポジトリで第三者に通知・記録が飛ぶのを防ぐ |
| AI テキスト全般 | `www.` で始まる文字列を D2（URL の禁止）の検出対象に含め、検出したら項目を除外する（囲んで残すことはしない） | GitHub は `http(s)://` がなくても `www.` で始まる文字列を自動でリンクにする。D2 は AI テキストの URL を全面的に禁止するので、他の URL と同じく除外する |
| 表のセルに入る AI テキスト | `\|` をエスケープする | 表の崩れを防ぐ |
| AI テキスト全般 | 文字数の上限（1.3）はプロンプトで指示するだけにする。検証では、上限の2倍を超えたときだけ項目を除外する | 上限ちょうどで除外すると、少し長いだけの有用な項目が消える。2倍を超えるものは構造の崩れや長い引用（D4）の疑いが強い |
| 出典のリンク文字列 | 外部記事のタイトルは使わず、設定ファイルの情報源名（例：`Hacker News`）とドメインだけにする | 外部のタイトルには指示や誤誘導の文言を書ける。リンク文字列も読者が信じる部分なので、外部由来の自由文を入れない |
| GitHub のリポジトリ名 | `owner/repo` の形式だけを許し、インラインコードで囲む | 同上 |
| 本文全体 | 投稿直前に秘匿情報を検査する（US-E7-05）。本文が 60,000 文字を超えたら不合格にする | GitHub の Issue 本文には文字数の上限がある（65,536 文字とされる。未確認で、PoC で確かめる）。日次・週次の通常量では届かない |

D-07 の D3（HTML の禁止）には HTML コメント（`<!--`）も含める。AI テキストにコメントがあると、それ以降の本文が表示されなくなったり、4章の識別子を偽装されたりするため。

### 0.4 日付・時刻の表記

- 日付は JST で `YYYY-MM-DD（曜）` とする。出典の日付は曜日なしの `YYYY-MM-DD`
- 公開日が不明で投稿日を使う場合は `投稿 YYYY-MM-DD` と書き分ける（公開日は `公開 YYYY-MM-DD`）
- 実行日時は `YYYY-MM-DD HH:MM JST`

## 1. 日次レポート Issue

### 1.1 タイトル

```
[日次] {{C: 対象日 YYYY-MM-DD（曜）}}の技術動向
```

- 例：`[日次] 2026-10-23（金）の技術動向`
- 対象日（前日）を入れ、実行日は入れない。タイトルと中身の期間を一致させるため
- 先頭の `[日次]` はラベル（D-08）と重複するが、通知メールの件名で日次か週次かを分かりやすくするため付ける
- 件数・部分レポートの印はタイトルに入れない。件数は本文冒頭に、取得できなかった情報源は本文末尾に書く

### 1.2 本文の構成

上から順に並べる。★ は読者が必ず読む部分。

| # | セクション | 書く主体 | 内容 |
|---|---|---|---|
| 0 | 識別子 | コード | HTML コメント（4章）。表示されない |
| 1 | ヘッダ ★ | コード | 対象期間・掲載件数。件数が少ない日は定型文を加える（1.5）。急上昇を判定しなかった情報源があれば定型文を加える（1.6）。0件の日は、目次とカテゴリ別の項目の代わりに「該当なし」の定型文が入る（1.5） |
| 2 | 目次 ★ | コード | カテゴリ名と件数。0件のカテゴリも「0件」と出す（US-E2-04） |
| 3 | カテゴリ別の項目 ★ | コード＋AI | 5カテゴリの固定順。各項目は 1.3 の形式 |
| 4 | フッタ | コード | 評価コメントの書き方（US-E7-03）、自動生成である旨 |
| 5 | 取得できなかった情報源 ★ | コード | 本文の最後に置く（US-E6-03 の「末尾」）。1件以上あるときだけ出す。折りたたまない |

カテゴリの固定順と内部値（`category` の enum）：

| 順 | 表示名 | enum |
|---|---|---|
| 1 | 生成AI・LLM・AIエージェント | `ai` |
| 2 | 開発者ツール | `devtools` |
| 3 | クラウド・インフラ | `cloud` |
| 4 | OSS | `oss` |
| 5 | その他の新テーマ | `other` |

- 項目が0件のカテゴリは見出しごと省き、目次に「0件」と出す。空の見出しが並ぶと読み飛ばしの手間が増え、0件であることは目次で分かるため
- カテゴリ内は重要度の高い順に並べる。並び順は AI が `rank` で返し、コードが並べる
- 項目番号はカテゴリをまたいだ通し番号にする（例：項目1〜15）。コメントで「項目3 は誤検出」と指せるようにするため。`#3` 形式は GitHub が Issue #3 へのリンクにしてしまうので使わない
- 目次は件数の一覧にとどめる。Issue 本文の見出しに目次から飛べるアンカーが付くかは未確認で、PoC で確かめてから目次をリンクにするかを決める

### 1.3 項目の形式

各項目は6要素（US-E2-03）を持つ。カテゴリはカテゴリ見出しで示し、項目内には繰り返さない（US-E2-03 の「各項目にカテゴリ」は所属する見出しで満たす）。

**標準形**（重要度の高い項目。US-E2-05）

```markdown
#### {{C: 通し番号}}. {{AI: 日本語の見出し（40字以内）}}

- **要点**
  - {{AI: 要点1（80字以内）}}
  - {{AI: 要点2（任意。最大3つ）}}
- **重要性**：{{AI: 重要性の理由（100字以内）}}
- **期間内の出来事**：{{AI: 期間前に公開された項目のみ。期間内に何が起きたか（60字以内）}}{{C: 急上昇の数値があれば「（Star +1,234／24時間）」}}
- **出典**：{{C: 一次情報 [情報源名（ドメイン）](URL) 公開 YYYY-MM-DD}} ／ {{C: [情報源名（ドメイン）](URL) 投稿 YYYY-MM-DD}} …
```

**簡潔形**（重要度の低い項目。US-E2-05）

```markdown
#### {{C: 通し番号}}. {{AI: 日本語の見出し}}

{{AI: 要点（1文、80字以内）}} **重要性**：{{AI: 理由（1文、60字以内）}}
{{AI: 期間前に公開された項目のみ「期間内の出来事：」に続けて1文（60字以内）}}{{C: 急上昇の数値があれば「（Star +1,234／24時間）」}}
出典：{{C: [情報源名（ドメイン）](URL) 公開 YYYY-MM-DD}}
```

- 標準形か簡潔形かは AI が `depth`（`full`／`brief`）で返す。標準形の件数はプロンプトで目安を示すだけにし、検証はしない
- 出典の並びはコードが決める。`primary_link_id`／`primary_item_id`（D-06）を先頭にし、残りは `item_ids` の順。一次情報には文字の印 `一次情報` を付ける（読み上げ・検索でも分かるよう、絵文字は使わない）。一次情報が特定できない項目は印を付けない。出典はすべて並べる
- 「期間内の出来事」は、標準形・簡潔形のどちらでも、期間前に公開された項目（急上昇など）のときだけ出す。必要かどうかはコードが公開日と対象期間から判定し、必要なのに AI の出力にない場合は項目除外（US-E7-01 の必須項目）
- 急上昇の数値は、Star の増分なら対象日 6:00〜翌日 6:00 の24時間の値（D-13）
- 文字数の上限はプロンプトで示す目安で、検証での除外は上限の2倍を超えたときだけ（0.3）。20件・平均 300 字で約 6,000 字となり、日本語の読む速さ（1分あたり 500〜600 字程度とされる）で10分前後に収まる。上限と倍率は、PoC で数日分を人が読んで調整する

### 1.5 件数が少ない日・0件の日（US-E2-06）

- 0件：目次とカテゴリ別の項目の代わりに、コードが次の定型文を入れる

  > **該当なし**：対象期間に、掲載基準を満たす重要な技術情報はありませんでした（収集 M 件）。ジョブは正常に完了しています。

- 少ない日（1件以上、しきい値未満）：ヘッダに次の定型文を入れ、通常どおり項目を載せる。しきい値はコードの固定値とする（初期値は5件。PoC で調整する）

- 「ジョブは正常に完了しています」を入れるのは、US-E2-06 の目的（Issue がない＝失敗、と区別する）を本文でも明確にするため
- 除外で0件になった場合は、レポート Issue ではなく不合格 Issue になる（US-E7-02）。全情報源の取得失敗は実行エラー Issue になる（US-E6-04）

### 1.6 急上昇を判定しなかった情報源（D-13）

ある情報源について前日の取得の記録が丸ごとなく、前日比が必要な判定（人気型フィードへの初登場、GitHub の Star の増分）を行わなかった日は、その判定ごとに次の定型文を1行、ヘッダに入れる。人気型フィードのように情報源が複数ある判定では、記録がなかった情報源の名前を並べる。

> ℹ️ {{C: 判定の名前（例：GitHub の Star の急増）}}は、前日の記録がないため判定していません。

- 初めて見る個々のリポジトリ・記事については入れない
- 決まった動きなので、部分レポートとして扱わず、「取得できなかった情報源」にも書かない

## 2. 週次レポート Issue

### 2.1 タイトル

```
[週次] {{C: 対象週 YYYY-MM-DD（月）}}号 技術トレンド（{{C: 調査期間 MM/DD〜MM/DD}}）
```

- 例：`[週次] 2026-10-26（月）号 技術トレンド（10/19〜10/25）`
- 対象週の識別は、US-E4-03 のとおり「本来の実行日であるその週の月曜」の日付にする。ただし月曜の日付だけでは「その週の動向」と誤読されやすいので、`号` を付けて発行日であることを示し、調査期間を括弧で添える
- 調査期間は未確定事項3（[concept.md](../concept.md#未確定事項)）で決める。設定で変えても（US-E8-01）対象週の識別は変わらないので、タイトルの括弧内だけが変わる。調査期間が年をまたぐ場合は `2026/12/28〜2027/01/03` のように年を付ける

## 3. 不合格 Issue・実行エラー Issue

### 3.1 タイトル

不合格・実行エラーは実行ごとに作るため（US-E6-04・E7-02）、タイトルに実行日時を入れて区別する。ただし秘匿情報検出の定型 Issue は、タイトルにも実行日時を入れない。

タイトルの扱いが種別で違うのは、要件の縛り方を次のように読み分けるため。

- US-E7-05 は「定型の実行エラー Issue（…・対象期間・処理段階のみ）」と Issue 全体を縛る。タイトルも「のみ」の対象とし、実行日時を入れない。実行ID は DB のレポートと Issue の対応（US-E5-03）から Issue 番号で引ける
- US-E7-04 は「定型の項目のみが書かれ」と本文の記載項目を縛る。タイトルは記載項目に数えず、実行ごとの区別のため実行日時を残す

| 種別 | タイトル | 例 |
|---|---|---|
| 不合格 | `[不合格][日次] {{C: 対象日}}のレポート（{{C: 実行日時}} 実行）` | `[不合格][日次] 2026-10-23（金）のレポート（2026-10-24 06:00 実行）` |
| 実行エラー | `[実行エラー][週次] {{C: 対象週}}号（{{C: 段階}}・{{C: 実行日時}} 実行）` | `[実行エラー][週次] 2026-10-26（月）号（① 収集・2026-10-26 07:00 実行）` |
| 実行エラー（秘匿情報検出） | `[実行エラー][日次] {{C: 対象日}}（公開停止）` | `[実行エラー][日次] 2026-10-23（金）（公開停止）` |

### 3.2 共通の構成

AI が調査できた場合の構成。AI を利用できない場合は 3.5、秘匿情報検出時は 3.6 の定型だけにする。

| # | セクション | 書く主体 | 内容 |
|---|---|---|---|
| 1 | 概要（定型の項目） ★ | コード | 対象期間・実行ID・実行日時・（不合格）不合格となった検証項目／（実行エラー）失敗した処理段階・エラーの概要・再試行回数 |
| 2 | 調査結果 ★ | AI（④）＋コード（根拠の抜粋） | 発生した事象／推定される原因と根拠／調査内容／対策案（US-E7-04） |
| 3 | 付記 | コード | `<details>`：情報源ごとの取得結果、検証結果の詳細 |
| 4 | フッタ | コード | 自動では修正しない旨 |

- 不合格・実行エラー Issue には識別子を付けない。重複判定はレポート Issue だけが対象で（US-E4-03）、識別子を使う処理がないため
- 定型の項目はすべてコードが書く
- 「エラーの概要」は、コードが例外の種類を分類した短い文にする（例：`GitHub API が HTTP 429（レート制限）を返した`）。例外メッセージやスタックトレースをそのまま貼らない（US-E6-04）。例外メッセージにはパスや設定値が混ざりうるため
- 不合格 Issue には、生成されたレポート本文も、除外した項目の中身も書かない（US-E7-01・E7-02）。除外の件数だけを理由別に出す（例：`URL 不正 2 件、期間外 3 件`）。件数は項目そのものではないので「Issue に書かれない」に反しないものとして扱う
- `<details>` の中で Markdown を使うには、`</summary>` の後と `</details>` の前に空行が必要
- 対策案に「対象日を指定して再実行する」は書かせない。失敗した期間のレポートは作り直さないため（US-E6-05）

**根拠の抜粋**（US-E7-04 の短い抜粋）は AI に書かせない。

- コードが ④ の入力として、ログ・検証結果の行に ID（例：`L012`）を付けて渡す。AI は根拠に使う行の ID を `evidence_line_ids` で返すだけにする
- コードは、選ばれた ID の行を元のログから取り出して本文に入れる。存在しない ID は捨てる。上限は1ブロック10行以内・全体で3ブロックまで
- 除外した項目の本文・タイトルを含む行は、候補の行に入れない（US-E7-01 の「Issue には書かれない」）。項目は ID と除外理由だけで表す
- 抜粋には外部コンテンツの断片が入りうるため、必ずコードブロックに入れる（メンション・リンク・Markdown として解釈させない）。コードフェンスは、中身に含まれる最長のバッククォートの連続より長くする（最低3つ）。中身でフェンスを閉じられないようにするため
- 抜粋も投稿前の秘匿情報検査の対象（US-E7-05）

本文は次の固定文だけにする。US-E7-05 の「秘匿情報検出のため公開を停止したこと・対象期間・処理段階のみ」に合わせ、実行ID・実行日時・識別子は入れない。検出した情報の種類・位置・該当文字列は書かない（何が漏れかけたかの手がかりも公開しないため）。調査結果も載せない。

```markdown
秘匿情報の可能性がある文字列を検出したため、Issue の公開を停止しました。

| 項目 | 値 |
|---|---|
| 対象期間 | {{C: 期間}} |
| 処理段階 | {{C: ③ 検証・検査／⑤ 投稿}} |
```

- 処理段階は、検出した検査の段階（③ の秘匿情報の検査か、⑤ の投稿直前の検査か）をコードが入れる
- ログを探す手がかり（実行ID）は Issue に書かず、DB の「レポートと Issue の対応」（US-E5-03）から Issue 番号で引く

## 4. 重複防止用の識別子

### 4.1 埋め込み方

レポート Issue の本文の1行目に、コードが HTML コメントで識別子を書く。不合格・実行エラー Issue には付けない（重複判定の対象外で、使う処理がないため。3.2）。

```
<!-- tech-researcher kind=report cadence=daily target=2026-10-23 run=20261024-060000-a1b2 -->
```

| キー | 値 | 用途 |
|---|---|---|
| `tech-researcher` | 固定 | 本ツールの識別子であること |
| `kind` | `report` | 種別。人がラベルを付け替えても、本文でレポート Issue と確かめられる |
| `cadence` | `daily`／`weekly` | ラベル `cadence:*` と1対1 |
| `target` | 日次は対象日、週次は対象週の月曜（`YYYY-MM-DD`） | 重複判定のキー（US-E4-03）。調査期間の設定は含めない |
| `run` | 実行ID | DB の実行履歴との対応（US-E5-03）。4.3 で DB を補うときに使う。重複判定には使わない |

- 形式の版（`v1` など）は付けない
- HTML コメントは GitHub の表示では見えず、本文の編集画面と API で取得した本文には残る
- 1行目に固定し、正規表現で1行目だけを読む。AI テキストには HTML コメントを入れさせない（0.3、D-07 の D3）ので、本文の途中に偽の識別子があっても無視できる
- 値は英数字と `-` だけにする。HTML コメントの中に `--` を作らないため
- ヘッダにも対象期間を表示するので、人が見て分かる情報と機械用の識別子が両方ある

### 4.2 ラベル（D-08）との対応

| 種別 | 日次 | 週次 |
|---|---|---|
| レポート | `type:report`、`cadence:daily` | `type:report`、`cadence:weekly` |
| 不合格 | `type:rejected`、`cadence:daily` | `type:rejected`、`cadence:weekly` |
| 実行エラー（秘匿情報検出の定型も同じ） | `type:run-error`、`cadence:daily` | `type:run-error`、`cadence:weekly` |

### 4.3 重複判定の手順

レポート Issue を作る直前（⑤）に、コードが次の順に確かめる（US-E4-03）。

1. DB に、同じ `cadence`・`target` のレポート Issue の番号の記録があれば、その番号の Issue を GitHub から取得する
   - 存在する（Open・Closed を問わない）：作らない。Projects に未登録なら登録だけを行い、終了する
   - 転送済み（HTTP 301）：転送先の Issue を記録として扱い、DB を転送先で更新する。以降は「存在する」と同じく作らない
   - 見つからない（HTTP 404）：削除の可能性があるが、トークンの権限不足でも 404 になるため、ここでは作らずに 2 へ進んで確かめ直す。2 でも見つからなければ、運用者が削除したとみなして 3 へ進み、DB の記録は新しい Issue の番号で更新する（失敗した日を作り直さないので、これが起きるのは同じ実行の中の自動の再試行のときだけ）
   - それ以外（HTTP 410 など）：作らずに実行エラーとする。410 は主に Issues 機能が無効なときの応答で、削除を意味しない
2. DB に記録がない（または 1 で 404 だった）ときは、`type:report` と `cadence:{cadence}` のラベルが付いた Issue を Open・Closed を問わずページ送りで取得し、1行目の識別子の `target` が一致するものを探す
   - 見つかった：DB に記録を補い、1 の「存在する」と同じく、Projects に未登録なら登録だけを行い、終了する
   - 見つからない：3 へ進む
3. レポート Issue を作り、DB に番号を記録してから Projects に登録する

- 2 を行うのは、「Issue は作れたが DB への記録の前に落ちた」場合に、自動の再試行（US-E6-02）で重複させないため。DB だけを正にすると、この隙間で重複する
- 1 で GitHub から取得するのは、DB の記録だけでは Issue が削除されたことが分からないため
- DB に記録がなく、人がラベルを外していた場合は、2 で見つからず重複しうる
- 判定はレポート Issue だけを対象にする。不合格・実行エラー Issue は実行ごとに作る（US-E4-03・E6-04・E7-02）
- タイトルでは判定しない。人がタイトルを編集しうるため
- 検索 API は使わない。検索は字句解析（単語への分割）をしたうえで照合するため、識別子の完全一致の判定には当てにならない
- ドライラン（US-E8-04）では 1・2 の取得は行ってよいが、作成・登録・DB の更新はしない

### 4.4 前回までの Issue の Projects への登録

前回までに Projects への登録が失敗した Issue（種別と日次・週次を問わない）を、⑤ であわせて登録する（US-E4-03、D-04）。

- 登録しようとした Issue が見つからない（HTTP 404）場合は、Issue を作り直さず、ログと履歴に記録だけ残す。失敗した期間のレポートは作り直さないため（US-E6-05）

### 4.5 PoC で確かめること

- Issue 本文の文字数の上限（65,536 文字とされる）と、日次・週次の実際の文字数
- 文字数の上限で、実際に10分前後で読めるか（数日分を人が読んで確かめる）
- 0.3 の無害化で、メンション・参照・自動リンク・表の崩れが起きないか。攻撃文入りのテストデータで確かめ、D-07 の回帰テストに加える。テストデータには次を含める：`@ユーザー名`、`@org/team`、`#数字`、`GH-数字`、`owner/repo#数字`、コミット SHA、`owner/repo@SHA`、`www.` で始まる文字列、`|`、行頭の `#`・`>`・`-`、HTML コメント
- 根拠の抜粋（3.2）で、バッククォートを含むログ行がコードフェンスを閉じないか
- 4.3 の手順で、DB に記録がある Issue を削除したとき（404）に作れるか、転送した Issue が 301 を返すか、Issue 作成後に Projects 登録だけ失敗したとき登録だけが行われるか
