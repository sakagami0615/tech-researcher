# コンセプト（Why）

tech-researcher の存在理由と方針を定める。エピックは [epics.md](epics.md)、ユーザストーリーは [user-stories.md](user-stories.md) を参照する。

## 背景と課題

技術分野の動向は、GitHub・Hacker News・Reddit・X・公式ブログ・論文・日本語コミュニティなど多数の情報源に、日本語・英語で日々分散して発信される。これらを個人が毎日巡回するのは負担が大きく、巡回を怠ると重要なリリースや新しいOSSを見落とす。また、日々の断片的な情報からは、どのテーマが台頭し、どれが継続・沈静しているかという変化を捉えにくい。

## コンセプト

**大量の情報源を自分で巡回しなくても、毎朝の短時間で重要な技術動向を見落とさず把握でき、蓄積した観測から週単位のトレンドの変化を捉えられる。**

- 主軸：見落とし防止。前日の重要情報を、日本語の日次レポートとして毎朝届ける
- 副軸：変化の観測。収集・分析の履歴を蓄積し、週次レポートで台頭・継続・沈静したテーマを示す

新しいOSS・サービスとの出会い（発見）は、主軸を実現する手段の一つとして扱う。

## ペルソナ

| ペルソナ | 説明 |
|---|---|
| 読者 | 日次・週次レポートを読み、技術動向を把握する人（開発者本人） |
| 運用者 | 実行環境・設定・認証を管理し、失敗時に復旧する人（開発者本人） |

同一人物だが、得たい価値が異なるため分けて扱う。レポートは公開リポジトリの Issue として公開されるため、第三者に見られることを前提とする（ペルソナではなく制約として扱う）。

## 提供価値

- 読者：日本語・英語の複数情報源から選別された重要情報を、出典付きの日本語で短時間に読める
- 読者：日次の再掲ではない、変化に着目した週次のトレンド分析を読める
- 運用者：無人で定期実行され、失敗しても状況が Issue とログに残り、再実行で重複なく復旧できる

## 成功の基準

数値は目安とし、計測の仕組みは作らない。

- 日次：毎朝決まった時刻までに Issue が1件届き、10〜20件程度・10分前後で読み切れる
- 週次：毎週月曜に、何が台頭・継続・沈静したかが、日次の再掲ではない形で読める
- 見落とし：自分で別途知った重要ニュースがレポートに載っていないケースが少ない（人による定期評価で確認する。US-E7-03）
- 運用：無人で回り、障害時も再実行で重複なく復旧できる

## 方針

- 一次情報を優先し、レポートの各項目に出典URLを付ける
- 日付計算・重複排除・DB操作など決定的な処理はコードで行い、LLMには評価・要約・分析のみを任せる
- 同じ期間で再実行しても、レポートの Issue や DB レコードを重複させない
- レポートは公開されるため、認証情報や秘匿情報を Issue に出さない。収集した外部コンテンツには悪意ある指示が含まれうる前提で扱う
- 外部記事は要約と出典URLで紹介し、長い引用はしない
- 失敗時は生の出力を貼らず、原因の調査結果と対策案をまとめて Issue に残す
- 公開済み Issue の状態・本文・人のコメントは GitHub 側で管理し、自動で変更しない

## スコープ

MVPに含める：日次レポート、週次レポート（日次・週次それぞれの独自スキル）、情報収集（既存スキルの収集処理の再利用）、GitHub Issue 公開と Projects 登録、重複防止、履歴の蓄積、無人定期実行と基本的なリトライ、最低限のログ、自動品質検証、不合格・実行エラーの Issue 化と失敗の調査結果・対策案の記載、公開前の秘匿情報検査、外部コンテンツ中の指示への耐性、ドライラン、設定による期間・情報源の変更、Claude Code / Codex からの実行。

MVPに含めない（将来の構想）：

- 記事テーマ発掘・記事作成支援（蓄積データを将来の技術記事に活用する。自動執筆・公開は行わない）
- 外部通知・監視システム
- 速報専用の高頻度実行
- 公開済み Issue への追加調査・追記
- Claude Code / Codex の自動切り替え、モデル性能・コスト比較
- 複雑な技術ランキング
