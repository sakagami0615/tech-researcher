## MVP

### E1 技術情報の収集

日本語・英語の複数情報源から、重点領域（生成AI・LLM・AIエージェント、開発者ツール、クラウド・インフラ、注目度の高いOSS）と新しい技術テーマの情報を集め、重複をまとめる。見落とし防止の土台となる。

- 含む：情報源ごとの取得、対象期間による絞り込み、URL正規化と重複の集約、一次情報の特定
- 含まない：情報源の選定・優先順位の決定（PoCで決める）

### E2 日次レポート

前日（JST）の重要情報を10〜20件程度に選別し、毎朝読める日本語のレポートにする。コンセプトの主軸「見落とし防止」を直接実現する。

- 含む：重要度の判断、カテゴリに応じた調査深度、項目ごとの要点・重要性・出典の記載
- 含まない：速報（E11）

### E3 週次トレンド分析レポート

一定期間の観測と蓄積した履歴から、台頭・継続・沈静したテーマや比較・今後の注目点を分析する。コンセプトの副軸「変化の観測」を実現する。

- 含む：毎週月曜の分析レポート、過去の観測との比較
- 含まない：複雑な技術ランキング

### E4 GitHub への公開

レポートを公開リポジトリの Issue として作成し、個人 GitHub Projects に登録する。同じ期間のレポートを重複させない。

- 含む：レポート Issue・不合格 Issue・実行エラー Issue の作成と Projects 登録、ラベルによる種別の区別、重複防止
- 含まない：公開後の Issue の状態・本文の自動変更（E12）

### E5 収集・分析履歴の蓄積

収集情報・分析結果・実行履歴・Issue との対応を SQLite に最低1年間保存する。週次分析と障害調査の土台となる。

- 含む：収集情報、分析結果、実行ジョブとエラーの履歴、レポートと Issue の対応
- 含まない：GitHub 側の状態（Open/Closed、Projects のステータス、コメント）の二重管理

### E6 無人定期実行と障害復旧

Docker と cron で日次・週次を無人実行し、一時的な失敗はリトライし、復旧しない失敗は実行エラー Issue と記録に残して再実行で復旧できるようにする。

- 含む：定期実行、リトライ、部分レポート、実行エラー Issue、期間を指定した再実行、最低限のログ
- 含まない：外部通知・監視システム（E10）

### E7 レポート品質の担保

公開前にレポートを自動検証し、不備のある項目は除外し、レポート全体に不備があれば不合格 Issue として残す。失敗時は原因の調査結果と対策案を Issue にまとめ、修正に着手できるようにする。すべての Issue で秘匿情報の混入を防ぎ、外部コンテンツ中の指示に影響されないようにする。読者による評価を収集ルールやプロンプトの改善につなげる。

- 含む：自動検証、項目の除外、不合格 Issue、失敗の調査結果と対策案の記載、公開前の秘匿情報検査、外部コンテンツ中の指示への耐性、Issue コメントによる評価と手動での反映
- 含まない：評価結果の自動反映、LLM による自動再生成、コード・設定の自動修正

### E8 設定と実行環境の切り替え

調査期間・情報源を設定で変更でき、Claude Code / Codex のどちらでも実行でき、GitHub に登録せずに動作確認できるようにする。

- 含む：設定ファイルによる期間・情報源の変更、Claude Code / Codex での実行、ドライラン
- 含まない：Claude Code / Codex の自動切り替え、性能・コスト比較

## MVP外

| ID | エピック | 概要 |
|---|---|---|
| E9 | 記事テーマ発掘・記事作成支援 | 蓄積した情報から技術記事のテーマ発掘・追加調査・技術検証を支援する。自動執筆・公開は行わない |
| E10 | 外部通知・監視 | 実行失敗やレポート公開を外部に通知し、稼働を監視する |
| E11 | 速報 | 重要な発表を日次を待たずに高頻度実行で届ける |
| E12 | 公開済み Issue への追加調査・追記 | 公開後のレポートに追加調査の結果を追記する |
