# 実装ルール

設計・実装・設定ファイルの作成時に従うルール。

## 技術方針

- Claude Code と Codex の両方で開発できる構成にする（優先は Claude Code とする）。定期実行は Claude Code で行い、Codex での実行は MVP に含めない（[decisions.md](../spec/decisions.md) D-05）
- Python を中心に、CLI・API・AIエージェントを役割に応じて使い分ける
- 収集処理は [`last30days-skill`](https://github.com/mvanhorn/last30days-skill) のスクリプトを最大限再利用する
- 日次・週次は別スキルとし、共通処理は共有モジュールに置く
- 調査期間・情報源は設定ファイルで変更できるようにする
- AIモデル・外部サービスへの依存は差し替え可能な境界の内側に閉じる
- ツール・パッケージは最新のLTS版を使う（利用するSkillなどの制約がある場合はそちらに合わせる）

## 実装範囲

- 要件に書かれた機能だけを、最もシンプルな形で実装する
- 使われていないコード・設定・Skill・文書は削除する。ただし `third_party/` 配下の第三者コードはこの対象外とし、編集もしない（[decisions.md](../spec/decisions.md) D-01）
- 未実装の構想・将来対応は、「MVP後の対応」の GitHub Issue（ラベル `future`）1件にまとめて書く。着手するときは、その項目をレビューしやすい小さな作業単位の Issue（ラベル `dev`）に分け、その内容をもとに設計書更新・実装・動作確認を進める（[decisions.md](../spec/decisions.md) D-08）
- 次の場合は作業を進める前にユーザーへ相談する：要件にない機能の追加、重要な技術選定、仕様変更

## 処理の分担

- 日付計算・重複排除・DB操作など決定的な処理はコードで行い、LLMには判断・要約・分析のみを任せる
- 外部情報は一次情報を優先し、レポートの各項目に出典URLを付ける

## 安全性・冪等性

- APIキーや認証情報は環境変数から読み、コード・ログ・Issue本文には出力しない
- 処理は冪等にする：同じ期間の処理が再試行などで再び動いても、DBレコードやIssueが重複しない
